apaf.updater — Update Manager

Overview

The apaf.updater plugin provides a built-in update management UI and REST API for APAF. It allows an administrator to inspect installed plugins, discover available updates from remote update sites, resolve dependency trees, download plugin archives, install them into their target site, and perform rollbacks if needed.

All operations require the administrator security role.

Update Site Configuration

An update site is a remote HTTP/HTTPS server that exposes a plugin repository. The link between a local plugin site and its remote update source is declared in the site configuration file (siteConfig.json, or appConfig.json for Docker deployments) via the optional updateSiteUrl property on each site entry.

Site Configuration Format

{
  "sites": [
    {
      "id": "apaf",
      "location": "/opt/apaf/plugins",
      "updateSiteUrl": "https://my.update-server.com/repository/pluginMap.json"
    },
    {
      "id": "my-site",
      "location": "/opt/apaf/my-plugins"
    }
  ]
}

updateSiteUrl semantics

  • The property value can point directly to the pluginMap.json catalog file (e.g. https://host/repo/pluginMap.json) or to the base directory URL (e.g. https://host/repo) — both forms are accepted and normalised internally.
  • Sites that do not declare updateSiteUrl are ignored by the update checker; their plugins will never appear as removed or unknown.
  • Multiple sites may share the same updateSiteUrl; duplicate URLs are de-duplicated before catalog fetches are performed.

Update Site Repository Structure

The remote server is expected to expose the following layout under its base URL:
<baseUrl>/
  pluginMap.json                        // catalog file
  <pluginId>_<version>/
    manifest.json                      // remote plugin manifest
    <pluginId>_<version>.zip          // downloadable archive
The catalog file pluginMap.json must have the following structure:
{
  "plugins": [
    { "id": "apaf.security", "version": "1.1.0", "siteId": "apaf" },
    { "id": "apaf.admin", "version": "1.1.0", "siteId": "apaf" }
  ]
}

REST API

MethodPathRoleDescription
GET/apaf-updater/installedadministrator List all installed plugins with their version, site ID and dependencies
GET/apaf-updater/checkadministrator Compare installed plugins against remote update site catalogs and return a diff (added, updated, removed, unknown)
POST/apaf-updater/resolveadministrator Recursively resolve plugin dependencies against remote catalogs and manifests
POST/apaf-updater/downloadadministrator Download selected plugin ZIP archives into a temporary directory via an asynchronous managed job (npa.jobs)
POST/apaf-updater/installadministrator Extract and install downloaded plugin archives into their target site locations
GET/apaf-updater/checkpointsadministrator List all update checkpoints across installation sites
POST/apaf-updater/rollbackadministrator Revert plugins updated at a given checkpoint timestamp (LIFO — latest checkpoint only)
POST/apaf-updater/restartadministrator Request a server shutdown / restart

Update Workflow

A typical update session follows five steps:
  1. Check — call GET /check to discover which plugins have newer versions available on the configured update sites.
  2. Resolve — call POST /resolve with the selected plugins to compute the full dependency tree and confirm that all required plugins can be installed.
  3. Download — call POST /download to fetch the ZIP archives asynchronously. A job ID is returned; poll /apaf-jobs/:id to track progress.
  4. Install — call POST /install to extract the archives into their respective site directories. A checkpoint manifest is written automatically.
  5. Restart — call POST /restart to apply the newly installed plugins by restarting the NPA runtime.

Checkpoints and Rollback

After each successful install operation, the updater writes an update_<YYYYMMDD_HHmmss>.json manifest file inside each affected site directory. This file records:
  • The timestamp and ISO date of the update
  • The user who performed the install
  • The list of plugins installed or updated, with their previous version and target directory
These checkpoint files are used by POST /rollback to revert the most recent update. Only the latest checkpoint can be rolled back at any given time (LIFO rule). On successful rollback, the plugin directories added during that checkpoint are deleted and the checkpoint file is renamed to update_<timestamp>.json.reverted.

Dependency Resolution

The /resolve endpoint performs a recursive BFS over the dependency tree:
  1. It fetches pluginMap.json from the configured update site.
  2. For each target plugin, it downloads its remote manifest.json and inspects the requires array.
  3. Each unsatisfied dependency is looked up in the catalog. If the catalog version meets the version requirement, it is added to the install plan; otherwise it is reported as a missingDependency.
The response indicates whether the full set canInstall and provides the complete toInstall list and any missingDependencies.

Notes

  • Downloaded archives are stored under the OS temporary directory in a folder named apaf_updates/. They are not automatically cleaned up.
  • A site entry without updateSiteUrl is treated as a local-only site: its plugins are listed as installed but never compared against remote catalogs.
  • Version comparison uses a numeric segment-by-segment algorithm (e.g. 1.10.0 > 1.9.0).
  • The download step uses the apaf.jobs service to track progress asynchronously. Monitor job status before calling /install.
  • A server restart is required after installation for the new plugins to be loaded by the NPA runtime.
