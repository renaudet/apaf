apaf.user.datatype — User Datatype Plugin

Overview

The apaf.user.datatype plugin allows developers to define custom data schemas (user datatypes) and store typed records in CouchDB without writing any server-side code. Each user datatype is a JSON schema that describes a set of typed fields; the plugin automatically provisions a CouchDB database and exposes full CRUD REST APIs for both the schema definition and the data records.

On the client side, the DatatypeForm UI component renders an editable form for any user datatype instance. It is implemented in datatypeForm.js and is registered as the apaf.DatatypeForm component. Unlike the generic npaUiCore.Form component (which is APAF-unaware), DatatypeForm loads the datatype definition at runtime and derives the form layout and field types automatically from it.

Datatype Definition

A user datatype schema contains:

  • name — technical name (lowercase, no spaces); used in API paths and as the CouchDB database name
  • label — human-readable display label
  • description — optional description
  • persistent — true if records are stored in CouchDB
  • database — CouchDB database name (required when persistent is true)
  • private — true if records are visible only to their creator
  • readRole — security role required to read records (empty string = no restriction)
  • writeRole — security role required to create or update records (empty string = no restriction)
  • auditEnabled — true to record CRUD operations in the audit log
  • preProcessingCode — optional JavaScript code executed server-side before a create or update; may raise a veto by throwing an exception
  • postProcessingCode — optional JavaScript code executed server-side after a successful create (response already sent)
  • fields — array of field definitions (see below)

REST API — Datatype Definitions

All definition endpoints require the developer security role.

MethodPathDescription
POST/apaf-datatype/datatype/queryQuery user datatype definitions. Body: CouchDB Mango { "selector": { … } }; pass an empty body to return all.
POST/apaf-datatype/datatypeCreate a new user datatype definition. The authenticated user's login is stored in createdBy.
PUT/apaf-datatype/datatypeUpdate an existing user datatype definition. Body must include id and _rev. The authenticated user's login is stored in lastUpdatedBy.
DELETE/apaf-datatype/datatype/:idDelete a user datatype definition by UUID. Does not delete the corresponding CouchDB database or its records.
GET/apaf-datatype/datatype/:idRetrieve a user datatype definition by UUID.
GET/apaf-datatype/datatype/name?name=:nameRetrieve a user datatype definition by technical name.

REST API — User Data Records

All data endpoints require the operator role at minimum. Per-datatype readRole and writeRole restrictions are enforced in addition.

MethodPathDescription
POST/user-data/:datatypeName/queryQuery records of the named datatype. Body: CouchDB Mango { "selector": { … }, "fields": [ … ] }.
POST/user-data/:datatypeNameCreate a new data record. Body carries the record fields at root level. createdBy and created are injected automatically.
PUT/user-data/:datatypeNameUpdate an existing data record. Body must include id and _rev. lastUpdatedBy and lastUpdated are injected automatically.
DELETE/user-data/:datatypeName/:idDelete a data record by UUID.
GET/user-data/:datatypeName/:idRetrieve a data record by UUID.

Create / update body format: the HTTP request body carries the record fields directly at root level — there is no wrapper object such as { "data": { … } }. For updates, include both id and _rev at the root level for optimistic concurrency control.

Query body format: the body may include a CouchDB Mango selector to filter records, and an optional fields array to project only a subset of attributes in the response. Pass an empty body {} to return all records.

Pre- and Post-Processing

When a datatype definition includes preProcessingCode, the plugin evaluates that code as a function(ctx, oldRecord, record) before persisting the record on create and update operations. The function receives:

  • ctx.user — the authenticated APAF user object
  • ctx.runtime — the NPA plugin runtime
  • ctx.plugin — the apaf.user.datatype plugin instance
  • ctx.require — Node.js require
  • oldRecord — the previous record value (null on create)
  • record — the incoming record to be persisted (mutable)

Throwing any exception from the pre-processor raises a veto: the record is not persisted and a 500 response is returned with the exception message as the message field.

When a datatype definition includes postProcessingCode, the plugin evaluates that code as a function(ctx, record) after a successful create. The HTTP response has already been sent at that point; the post-processor runs asynchronously and its exceptions are logged but do not affect the client response.

Private Records

When private: true, the query handler filters the CouchDB results server-side and returns only records whose createdBy field matches the authenticated user's login. Administrator users always receive all records regardless of this flag.

Telemetry

The plugin tracks four telemetry dimensions, one per CRUD operation class. Each dimension receives a data point every 30 seconds containing the cumulative operation count since the last server restart:

  • create.user.datatype.count
  • read.user.datatype.count
  • update.user.datatype.count
  • delete.user.datatype.count

MCP Tools

The plugin registers MCP tools for both layers via npa.mcp.tool extension points in its manifest.

Schema tools (operate on datatype definitions):

  • queryDatatypes — query datatype definitions
  • getDatatypeById — retrieve a definition by UUID
  • getDatatypeByName — retrieve a definition by technical name
  • createDatatype — create a new datatype definition
  • updateDatatype — update an existing datatype definition
  • deleteDatatype — delete a datatype definition

Data tools (operate on user data records):

  • queryUserData — query records of a named datatype
  • getUserDataById — retrieve a record by UUID
  • createUserData — create a new data record
  • updateUserData — update an existing data record
  • deleteUserData — delete a data record

Notes

  • The CouchDB database declared in database is created automatically on the first request if it does not already exist.
  • Deleting a datatype definition does not delete the corresponding CouchDB database or any stored records.
  • After a create or update of a datatype definition, the plugin calls refreshDatatype() on the apaf.datatype plugin to invalidate the in-memory cache. This ensures that subsequent requests use the updated schema.
  • The DatatypeForm component supports a specializedEditors extension map: other plugins may register custom field type names at runtime, backed by a PluggableEditorField loaded from a plugin-provided JavaScript module. This is the recommended way to add custom field types without modifying datatypeForm.js.
