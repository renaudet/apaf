apaf.scheduler — Scheduler Plugin

Overview

The apaf.scheduler plugin manages the scheduled execution of code snippets and workflows. Scheduling rules are stored in CouchDB, evaluated periodically by a tick engine, and executed server-side without user interaction.

Scheduling Rule Types

TypeDescription
startupExecuted once when the server starts (or when the rule becomes active)
recurrentExecuted every delay minutes
fixedExecuted daily at the specified time (HH:mm:ss)

Data Model

A scheduling rule record contains:
  • name — human-readable name
  • type — startup | recurrent | fixed
  • active — boolean; only active rules are evaluated by the tick engine
  • servlet — UUID of the code snippet (fragment) to execute (mutually exclusive with workflow)
  • workflow — UUID of the workflow to execute (mutually exclusive with servlet)
  • runAs — UUID of the APAF user under whose identity the task executes
  • delay — repeat interval in minutes (for type recurrent)
  • time — execution time as HH:mm:ss (for type fixed)
  • lastExecuted — timestamp of the last execution (maintained by the engine)

REST API

MethodPathRoleDescription
POST/apaf-scheduler/queryadministratorQuery scheduling rules with a CouchDB Mango selector

PUT/apaf-scheduler/administratorUpdate an existing scheduling rule
DELETE/apaf-scheduler/:idadministratorDelete a scheduling rule

Tick Engine

The scheduler evaluates all active rules on a fixed interval controlled by the runtime property scheduler.tick.timeout (default: 30 000 ms). On each tick:
  • startup rules that have never been executed are triggered immediately.
  • recurrent rules are triggered if now - lastExecuted ≥ delay * 60 000 ms.
  • fixed rules are triggered if the current time matches the time field (within the tick interval).

MCP Tools

The plugin registers four MCP tools: querySchedulers, createScheduler, updateScheduler, deleteScheduler.

Notes

  • Updating a rule clears its lastExecuted field, which forces the scheduler to re-evaluate it on the next tick.
  • The runAs field controls the security identity used during execution — the resolved user must have the roles required by the target snippet or workflow.
  • Startup rules execute immediately at server start; to prevent re-execution after a restart, set the rule to inactive once it has run.
